STANDING PRACTICES:
  - Back up the database before any reseed or relabel that touches schema
    or ground-truth columns -- routine throughout this project's history,
    see the reseed entries above for examples.
  - For any comparison that spans MORE THAN ONE SCRIPT EXECUTION -- cross-
    seed, cross-window, before/after an intervention, or any other "run
    it again later and compare" test -- use database/ga_snapshot.py's
    frozen snapshot mechanism (activate_snapshot(name) + get_snapshot_
    origin(name)) instead of querying the live database directly. A
    silent live-database-drift confound (the order book and datetime.now()
    both move between runs) inverted two independently "confirmed" GA
    results before this was caught -- see GA_AGENT_POSTMORTEM.md Section 8
    for the full finding and Section 7f for the fix. Not limited to GA or
    memetic-integration work: the same risk applies to any script that
    labels a result by a selection rule (a window, a seed, a query) rather
    than a fixed dataset.
  - Any script producing an "authoritative" or multi-window comparison
    report must save the FULL PER-WINDOW, PER-STRATEGY BREAKDOWN into its
    JSON output -- not just a whole-book aggregate and a terminal/text
    narration of the per-window numbers. run_authoritative_comparison.py's
    first run (2026-08-27) saved only *_aggregate dicts; its printed
    per-window table showed a window's INCREMENTAL makespan next to a
    capacity-floor ratio computed from that window's CUMULATIVE makespan --
    both real, correctly computed numbers, but shown under one ambiguous
    column with nothing to check either quantity against, so the two
    looked inconsistent with no way to verify which (if either) was right.
    Caught by the user re-deriving the ratio by hand from the printed
    increments and finding it didn't reconcile -- not caught by anything
    in the pipeline, because the underlying per-window data was never
    persisted anywhere to check. Fixed by saving RESULTS['per_window'] =
    {strategy: [one full row per window: on-time%, cum_makespan_days,
    incr_makespan_days -- both explicit and separately labelled --
    throughput, tardiness, labour%, capacity_floor_days, capacity_floor_
    ratio, margin]}, so every printed number traces back to a saved,
    independently checkable value. Any future report generator (this one
    or reporting/evaluation_report.py) should do the same: a stated number
    a reader cannot verify against the saved artifact is not authoritative.
  - database/queries.py::fetch_active_orders_and_routings's three-table
    JOIN (plus a LEFT JOIN subquery) had NO ORDER BY -- row order was
    therefore genuinely UNDEFINED by SQL semantics, not merely unspecified-
    but-stable. Confirmed as a REAL, DIRECT cause of GA non-reproducibility
    (2026-08-27), not theoretical: two full runs of run_authoritative_
    comparison.py (identical seed, frozen snapshot, origin, GNN checkpoint)
    produced genuinely different schedules (window 2 GA margin: +8.18% vs
    +1.29%). Bisected stage by stage -- data loading, GNN inference, the 5
    baseline heuristics, optimize() alone (both toy and full scale),
    optimize()+polish() together -- all reproduced bit-for-bit in
    isolation, which pointed at something upstream of all of them.
    Confirmed directly: rebuilding the snapshot fresh (DROP+CREATE+re-clone,
    identical source data) and immediately querying it produced a THIRD,
    still-different result from either prior run, while every repeated
    query against one already-materialized, unchanging snapshot agreed with
    itself. Fixed with an explicit `ORDER BY po.production_order_id, ro.
    operation_sequence_number` -- not an arbitrary tie-break, but the
    ordering every downstream consumer already assumes (ga/fitness.py's own
    precedence check, ga/operators.py::repair_precedence, both keyed on
    operation_sequence_number). Verified directly: two independent fresh
    snapshot builds after the fix produced byte-identical, correctly
    grouped-and-sequenced row order (8,745/8,745 rows, zero violations).
    General lesson: ANY multi-table query without an explicit ORDER BY that
    feeds a chromosome-position-sensitive or precedence-sensitive pipeline
    should be treated as a live reproducibility risk, not merely a style
    nit -- "it happened to be stable in testing" is not evidence it will
    stay stable across a fresh table build.

SECTION 0J -- SIMULATION FIDELITY: ACTUAL TIMELINE IS NOW CASCADING
Measured 11 September 2026, on staging garment_fyp_db_seed_v2_20260911_061202
(dataset 91fa7403-180e-4af5-bf63-365e111fe4ed) vs. the pre-cascade live
database garment_fyp_db. Audit only; nothing was repaired.
===============================================================================

WHAT CHANGED. The seeder used to emit "planned-calendar dispatch schedules
with NON-CASCADING synthetic actual timestamps": each lot's actual finish was
a bounded perturbation of its own plan, so a late lot could never delay the
next one. It now streams "independent resource-constrained planned and
synthetic actual calendars" (seed_database_fixed.py), scheduling actuals
against real resource availability. Delay therefore PROPAGATES.

This closes a limitation this document previously acknowledged -- that actual
overruns did not cascade and the actual timeline was consequently not a
resource-constrained execution history. It is a fidelity IMPROVEMENT. It also
changes what several downstream numbers mean, which is why it is recorded
here rather than only in a code comment.

MEASURED BEFORE -> AFTER

  lots dispatched with zero queue        77.3%   ->  24.7%
  median queue delay at dispatch          0.0    ->  418.8  min
  mean queue delay at dispatch          589.2    -> 2720.0  min
  operation lateness p99                 23.4    -> 1864.7  min
  within-operation per-lot lateness SD    6.9    ->   68.7  min (median)
  decisive-lot agreement (planned-last
    vs actual-last)                      96.5%   ->  78.1%
  delay-label positive rate              10.86%  ->  28.33%
  mean lot duration (label denominator)  53.6    ->   57.6  min (median)

WHERE THE LATENESS NOW COMES FROM. Exact additive decomposition of per-lot
lateness, residual 0.000000 min, n=40,000:

  actual_start - planned_start   (dispatch/queue wait)   88.5% of variance
  actual_pause - planned_pause   (calendar/shift wait)   11.4%
  actual_prod  - planned_prod    (execution + repair)     0.1%

So the delay label is now QUEUE-DOMINATED. A positive label means "could not
start on time", not "ran long". Shift pauses are NOT the driver: 98.1% of
lots carry zero planned pause and only 1.9% have a span more than half pause.
Nor is branch load concentration: the two micro-branches show the LOWEST mean
start shift (NC8 63.0 min, CW3 40.1 min) against the largest (NCL 92.1 min),
i.e. capacity-weighted allocation is behaving correctly.

WHAT THE DENOMINATOR STILL MEANS. mean_lot_duration moved only 1.1x at the
median (53.6 -> 57.6 min; p25-p75 40.8-60.7). The 20% threshold is still a
~30-70 minute execution-scale bar. Only p95/p99 fattened (97.9 -> 178.3;
151.3 -> 331.0), tracking the same ~1.9% of paused lots.

CONSEQUENCES ALREADY APPLIED
  - graph/node_features.py: decisive-lot proxy strength restated 96.0% ->
    78.1%, and its "actuals closely track plan" premise retracted. The proxy
    stays leak-safe (that rests only on planned_end_time preceding execution)
    and remains the majority case, but ~1 operation in 5 attributes its
    decisive-lot features to a lot that was not actually last.
  - graph/labels.py: delay head documented as queue-dominated, with the
    decomposition above.

CONSEQUENCE NOT YET APPLIED -- OPEN
  - scratch/delay_dgp_ceiling.py computes its oracle as
    sim_actual_end = planned_start + lot_duration * variance_multiplier.
    It holds actual_start EQUAL TO planned_start by construction, so it
    models execution-variance multipliers ONLY and contains no start-shift
    term. Queue delay enters only as an SD-widening parameter on DURATION,
    never as a start displacement. Under this dataset that omits 88.5% of
    the lateness variance, so its "theoretical ceiling AP" no longer
    describes this label and must not be quoted for it without being
    reworked to displace starts as well as stretch durations.

SECTION 0B -- THE WINDOW-COLLAPSE INVESTIGATION: OVERLAPPING LOOKAHEAD
===============================================================================

Section 2.2 (below, from the previous version of this file) identified that
on-time rate collapses across later rolling-horizon windows -- 100% -> 99.3%
-> 80.7% -> 25.3% -> 6.3% in the Section 0 run -- and that this is NOT a
capacity wall (independently verified ceiling: 100%, 0 orders structurally
infeasible). The diagnosed cause: each 300-order window commits machines with
zero visibility into what the NEXT window's orders will also need.

THE FIX ATTEMPTED: textbook receding/moving-horizon control. Solve over a
LOOKAHEAD wider than what gets committed, lock in only the near-term slice,
slide forward by the commit size so the overlap gets re-optimised with fresh
information every round. Implemented in ga/rolling_horizon.py
(extract_committed_subschedule + run_rolling_horizon), commit=300 throughout,
tested at lookahead L = 300 (the original non-overlapping behaviour, L==C is
a no-op filter), 600 (2x) and 900 (3x). One process, one origin, one seed,
full order book:

  L      windows   on-time   makespan   throughput   mean tard   labour  runtime
  300       5        71.3%     71.4d       17.7/d        234h    36.7%     8.7m
  600       5        65.9%     78.7d       16.1/d        334h    33.3%    24.3m
  900       5        63.1%     83.7d       15.1/d        332h    31.3%    23.9m

RESULT: lookahead makes every measured outcome worse, MONOTONICALLY, while
costing ~2.8x the runtime regardless of whether L is 2x or 3x the commit
size. This is the opposite of the textbook expectation and the opposite of
what the diagnosis in Section 2.2 predicted. NOT adopted --
LOOKAHEAD_ORDERS stays None (commit-only, L==C) as the default in
run_final_pipeline.py.

WHY IT LIKELY BACKFIRES, given what else this project has established: the
fitness function optimised over the lookahead treats every order in it
symmetrically -- it has no notion of "these 300 are about to be locked in,
the rest are provisional." The GA is free to trade away near-term (soon to
be committed) punctuality to improve the schedule's AVERAGE performance
across the full lookahead, including orders that will simply be thrown away
and re-optimised next round regardless of how they scored this round. A wider
lookahead gives the optimiser more such orders to sacrifice the committed
slice for. Standard receding-horizon control usually weights the objective
toward the commit region specifically (or discounts the tail); this
implementation solves the whole lookahead with one flat objective, and that
refinement was not built this session -- it is the concrete next step if
this is revisited (Section 2.2, updated).

SECOND EXPERIMENT: shrink the commit chunk instead of widening the lookahead
-- the more literature-standard rolling-horizon pattern (frequent
rescheduling, large window overlap), which might sidestep the same failure
mode differently since it changes how OFTEN the objective gets to make that
trade rather than how MUCH lookahead it has to trade with. Tested
commit=100/lookahead=300 and commit=150/lookahead=450 against a same-process
commit=300/lookahead=300 baseline, one origin, one seed, full order book:

  C    L   win  on-time  makespan  throughput  mean tard  labour  runtime
  300  300   5    66.0%    72.0d     17.5/d       265h    36.4%    13.6m
  100  300  13    57.7%    95.4d     13.2/d       531h    27.5%    21.5m
  150  450   9    62.9%    78.2d     16.2/d       348h    33.5%    22.2m

RESULT: also worse on every axis, at ~1.6x the runtime -- a third independent
confirmation of the same diagnosis via an orthogonal mechanism. C=100
degrades more gradually than C=300's sharp cliff (100% for 4 of 13 windows,
sliding down rather than falling off after window 2), but ends up worse in
aggregate: more frequent commitment gives the flat, undifferentiated
objective more OPPORTUNITIES to trade near-term punctuality away, not fewer.
NOT adopted. Neither window geometry change helps without first fixing what
both point at: the objective needs to distinguish committed from provisional
orders. That fix is still not built.

Both experiments are recorded here, plainly, as genuine negative results:
the standard window-geometry techniques, applied in their textbook form, did
not help this system, in either direction (wider lookahead, or smaller/more
frequent commits). See Section 4, reversal 5.

SECTION 0C -- THE COMMIT-WEIGHTED OBJECTIVE FIX: MEASURED
===============================================================================

Section 0B's diagnosis, above: the fitness function scores the whole
lookahead symmetrically, with no notion of "committed vs provisional," so the
GA is free to trade committed-window punctuality for average performance
across orders that get thrown away and re-optimised next round anyway. The
concrete fix it called for: make the objective score only the orders actually
being committed this round.

IMPLEMENTED: ga/fitness.py::evaluate_schedule gained a scored_order_ids
parameter. When set, the makespan term and the entire deadline-lateness block
(on-time rate, mean/max tardiness) are computed ONLY over that set;
load_balance_penalty, idle_labor_penalty, the GNN delay-risk penalty and the
priority reward stay whole-lookahead deliberately -- those measure real
machine/labour usage and reward sequencing foresight across everything
actually simulated, not a claim about which orders are "done."
ga/rolling_horizon.py passes scored_order_ids=commit_ids automatically, so
every existing caller (GA evaluation, parallel workers, polish(),
run_baselines()) inherits it via the shared _eval_ctx with no other code
change. 7 new regression tests in tests/test_commit_weighted_objective.py;
full suite 149/149 passing. When lookahead==commit (the plain, non-overlapping
case), scored_order_ids equals the full lookahead, so this is a mathematical
no-op there -- confirmed by using that arm as this sweep's own control.

MEASURED, one process, one origin, one seed, full order book, fix ACTIVE
in every arm (2026-08-15, same dataset as Section 0B, not reseeded):

  C    L   windows  on-time  makespan  throughput  mean tard  labour  runtime
  300  300    5       66.3%    73.8d     17.1/d       296h    35.6%    14.7m   <- L==C, control
  300  600    5       65.8%    77.0d     16.4/d       271h    34.1%    29.0m   (-0.5pp vs control)
  300  900    5       58.6%    82.9d     15.2/d       383h    31.6%    58.1m   (-7.7pp vs control)
  100  300   13       58.0%    85.9d     14.7/d       431h    30.5%    38.6m   (-8.3pp vs control)
  150  450    9       55.7%    94.3d     13.4/d       447h    27.8%    24.6m  (-10.6pp vs control)

RESULT: mixed, and reported honestly rather than rounded up. The fix clearly
did something real -- at a 2x lookahead/commit ratio (L=600), the degradation
versus the plain baseline shrank from -5.5pp (Section 0B, unfixed objective)
to -0.5pp (fixed), a large reduction in harm. But it did NOT turn any tested
overlapping-window geometry into a net win over the plain C=300/L=300
baseline, and at a 3x ratio -- whether reached by widening lookahead (L=900)
or by shrinking the commit chunk (C=100 or C=150, both textbook
literature-standard geometries) -- the degradation is essentially as bad as
before the fix (L=900: -7.7pp fixed vs -8.2pp unfixed) or WORSE than before
the fix (C=150/L=450: -10.6pp fixed vs -3.0pp unfixed in Section 0B's
unfixed run). That last number is not noise-sized and is the opposite of
what fixing the objective was supposed to do to that arm.

WHY THE 3x-RATIO ARMS LIKELY GOT NO BETTER (OR WORSE): scoring only the
committed subset removes the GA's incentive to keep the PROVISIONAL two-
thirds of the lookahead in good shape, since their own lateness no longer
counts. At a 2x ratio, half the lookahead is still committed, so provisional
neglect has limited room to hurt; at a 3x ratio, two-thirds of every window's
simulated work is provisional, and machines the GA leaves in a poor state for
that two-thirds are exactly the machines next round's real commitment
inherits. The original symmetric objective at least gave provisional orders
SOME reason to be scheduled sanely; this fix removes that reason precisely
where the uncommitted fraction is largest. The fix traded "committed orders
are scored as if provisional" for "provisional orders are scored as if they
don't matter," and which trade wins depends on the uncommitted fraction --
net positive at 2x, net flat-to-negative at 3x in both geometry families
tested.

DECISION: NOT adopted as a way to enable overlapping lookahead or a smaller
commit chunk -- no tested geometry, even with the fix active, beats the
plain non-overlapping C=300/L=300 baseline on-time rate (66.3%) in this
dataset. run_final_pipeline.py's default (LOOKAHEAD_ORDERS = None, i.e.
L==C) is unchanged and remains correct. The fix itself (scored_order_ids)
stays in the codebase -- it is provably a no-op at the shipped default, it
measurably reduces (does not eliminate) harm at moderate overlap should that
be revisited, and correctly distinguishing committed from provisional work is
the right objective regardless of whether a geometry that benefits from it
has been found yet. See Section 4, reversal 6.

SECTION 0D -- THE GNN DELAY LABEL: EXECUTION VARIANCE, MEASURED (TWICE)
===============================================================================

Prior finding (Section 2.3/3, historical): the delay classifier scored near
the no-skill baseline on every run (F1 0.0, AP ~= positive rate, ROC AUC ~=
0.5) because the label was `1.0 if execution_status in ['Delayed','Failed']
else 0.0`, and execution_status only ever turned Delayed/Failed for a lot the
SEEDER'S OWN now_time snapshot considered already started -- everything
scheduled later was unconditionally 'Scheduled', so the label was ~99.9%
equivalent to "has this operation started", not a risk signal. Proposed fix,
approved: add genuine execution-time variance to the seeder, independent of
simulation progress, and derive the label from real lateness against each
operation's own plan.

IMPLEMENTED. data_generation/seed_database_fixed.py gained
sample_execution_variance_multiplier() (clipped normal, mean 1.0, sd 0.15,
range [0.65, 1.6], endorsed defaults) applied per lot on top of its planned
work duration, and two new columns -- actual_start_time, actual_end_time --
recording synthetic perturbed timing, not observed outcomes. Machine/worker
availability and routing precedence advance using planned ends, not actual
ends. Actual overruns do not cascade; this is not a fully resource-constrained
actual execution timeline. planned_start_time/planned_end_time
keep their EXISTING meaning unchanged (the committed schedule floor
decision_engine/impact_assessor/GAScheduler already depend on) -- zero risk
to those consumers. database.queries.fetch_actual_vs_planned_timing() feeds
this, unfiltered by execution_status or now_time, ONLY into
graph/labels.py::extract_gnn_labels -- never into node features. Database
backed up first (backups/pre_delay_label_fix_<timestamp>.sql), then reseeded.

ATTEMPT 1 (a genuine, measured failure -- reported here rather than
quietly fixed and forgotten): the label aggregated each operation's delay as
the MEAN of its ~60 parallel lots' individual lateness. Retrained and
measured:

  positive_rate   0.0000
  delay_accuracy  1.0000   delay_precision  0.0000
  delay_recall    0.0000   delay_f1         0.0000
  average_precision  0.0000   roc_auc  NaN (single class in validation set)

A second, different degenerate label. Diagnosed: averaging ~60 roughly-
independent per-lot variance draws (sd 0.15 each) crushes the aggregate's
spread by ~sqrt(60) (Central Limit Theorem) to a standard error of ~1.9%,
nowhere near the 20% threshold. Confirmed directly against the reseeded
database: mean-lateness-fraction ranged -6.3% to +8.1% across all 7,500
operations -- NEVER once crossing 20%. positive_rate=0.0 was not a modelling
failure, it was arithmetic: the aggregation choice made the label
unconditionally 0 regardless of what the model could possibly learn.

FIX (before re-measuring, not after -- this was caught by evaluating the
retrained model, exactly what Part C's "the real test" was for): an
operation's quantity is split across ~60 PARALLEL lots -- real machine-level
concurrency, not independent repeated trials -- and the operation genuinely
isn't complete until its LAST lot finishes, exactly how ga/fitness.py already
treats an operation's own completion (max across its chosen machines). Lots
also queue onto machines over an extended window (mean per-operation span
~944 minutes), so measuring lateness against that whole span (rather than
against the ~30-70 minute scale a single lot's variance actually operates
at) was a SECOND, compounding bug in the same first version -- confirmed by
simulation: even switching to a last-lot-finishes lateness measure while
still dividing by the whole multi-lot span kept every operation under 5%.

Corrected graph/labels.py::_aggregate_actual_vs_planned: lateness =
(latest actual finish) - (latest planned finish) across an operation's lots,
divided by the MEAN SINGLE-LOT planned duration. Confirmed against the same
reseeded database before retraining: 7.7% of all 7,500 operations now cross
the 20% threshold -- a real, non-constant, non-degenerate distribution.
Tests updated (tests/test_delay_label.py) to encode this "last lot to finish
gates completion" semantics explicitly, replacing the disproven "averaged
across lots" version.

RETRAINED (no reseed needed -- only the label-derivation logic changed, the
seeded data was already correct) and measured, the real test:

  positive_rate      0.0880   (val set, 1,296 held-out operations)
  delay_accuracy     0.9120   delay_precision   0.0000
  delay_recall       0.0000   delay_f1          0.0000
  average_precision  0.0950   (no-skill = positive_rate = 0.0880)
  roc_auc            0.5218   (no-skill = 0.500)

HONEST READING: the LABEL is fixed -- positive_rate is a real, non-constant
8.8% rather than a leaked proxy for elapsed time or a divide-by-CLT artefact,
and by construction (df_actual_vs_planned is never merged into node
features, and never filtered by execution_status or now_time) it cannot
re-develop either of the two leaks already found and closed this session.
But the CLASSIFIER is still barely above the no-skill floor on it: AP
(0.095) is only marginally over the positive rate itself, ROC AUC (0.522) is
only marginally over random, and at the default 0.5 threshold the model
still never predicts positive at all (precision/recall/F1 all 0.0, accuracy
0.912 ~= 1 - positive_rate -- the same "always predict the majority class"
shape as before, just no longer because the label was defective).

This is not a measurement failure, it is the LIKELY correct outcome given
what's actually predictable here: the execution-variance multiplier is
designed to be believable but i.i.d. per lot -- routine noise, not a
signal tied to anything the GNN could see. The seeder's DISCRETE causal
delay factors that genuinely could be predictable (machine breakdown state,
employee leave, queue congestion, an approaching deadline) already exist in

0H.10 -- PRIORITY HEAD (HEAD 3) RE-GROUNDED: DEADLINE-URGENCY LABEL,
       TWO DESIGNS TRIED, PERCENTILE-RANK KEPT

The old Head 3 label was `max(0.1, 1.0 - operation_sequence_number * 0.15)`
-- a non-functional target. It depended ONLY on routing step (5 fixed
values, one per sequence position), never on the order's actual deadline,
so a body-assembly step on a slack-rich order always scored 0.85 and a
tubular-sleeve-join step on a deadline-critical order always scored 0.25 --
backwards from what ga/fitness.py's total_priority_reward actually wants
("pull genuinely urgent work earlier"). It also carried nothing for the
model to learn from graph context: sequence position is a trivial function
of routing order the precedence edges already encode structurally.

ATTEMPT 1 (measured, rejected): agent/fuzzy_logic.py::urgency_score, the
same function the live breakdown-triage agent uses to rank orders.
Grounded slack_days in the operation's own planned_start_time (preferred,
varies within an order) falling back to the order's release_date, then
passed straight through urgency_score's trapezoid membership. Measured
against the real 7,485-operation database BEFORE shipping (per this
project's standing measure-first discipline): 97.8% of operations came
back exactly 0.0. Traced, not assumed: every order in this database has AT
LEAST 21 days of release-to-deadline budget (measured range 21-75 days,
mean 46), and even the single most time-pressured operation in the entire
dataset never had less than ~14.6 days of slack at its own planned start --
urgency_score's anchors (SLACK_URGENT_FULL=3, SLACK_RELAXED_FULL=20 days),
tuned for the LIVE agent's real-time, days-scale judgment, don't span this
dataset's actual scale at all, so almost every operation landed in the
trapezoid's flat-zero tail. Same practical failure shape as earlier
degenerate labels (near-total saturation), different mechanism (anchor/
dataset-scale mismatch, not leakage). Presented to the user with three
options (dataset-scaled anchors as a new urgency_score parameter, keep
urgency_score as-is and accept the saturation, or drop the trapezoid
entirely) -- the user chose the third.

ATTEMPT 2 (kept): raw slack_days, converted to a [0,1] label by PERCENTILE
RANK within the operation set being labelled, instead of any fixed
day-scale anchor. graph/labels.py::
  - _slack_days_for(order_deadline, planned_start, release_date) -- same
    reference-point fallback chain as attempt 1 (operation's own
    planned_start, from the same leak-free source Head 2 uses, else the
    order's release_date), returns raw days or None (not 0.0) when there's
    no usable deadline/reference at all.
  - _percentile_rank_priority(slack_by_idx, num_nodes) -- (rank-1)/(n-1)
    over every operation with valid slack, then priority = 1 - percentile,
    so the least-slack operation in the batch always lands at 1.0 and the
    most-slack always at 0.0, regardless of the batch's absolute day-scale.
    Self-calibrating by construction -- cannot repeat attempt 1's failure
    mode against any future dataset, whatever scale it turns out to use.
    Missing-slack operations are excluded from the ranking population
    (so they can't distort everyone else's percentile) and default to a
    neutral 0.5, matching every downstream consumer's own missing-priority
    fallback (ga/fitness.py, agent/decision_engine.py: {'priority': 0.5}).
    Fewer than 2 distinct valid slack values (nothing to rank) also
    defaults everyone to 0.5 rather than an arbitrary tie-break.
  - extract_gnn_labels collects slack during its per-row pass (reusing the
    same planned-span lookup Head 2 already computes) and converts the
    whole batch to percentiles in one pass afterward, since ranking needs
    the full distribution, not one row at a time.

RESULT, stated plainly: Arm A beats Arm B (real signal exists -- this is
not a repeat of the old degenerate-label problem) but does NOT beat the

zero graph structure) already matches or edges out the GNN on RMSE and R2.
C2 (RandomForest on the same 7 numbers) clearly beats the GNN on every
metric -- 17% lower MAE, 18% lower RMSE, R2 0.52 vs 0.29. The full
heterogeneous message-passing architecture is not earning its complexity
for this head: a plain non-graph regression over the operation's own
visible attributes does the job better.

TWO PLAUSIBLE CAUSES, not mutually exclusive, neither pursued without
sign-off:
  1. Loss weighting: models/train.py combines the three heads as
     `loss_delay + (0.001 * loss_completion) + loss_priority`. Completion
     loss is raw-minutes-scale Huber loss (hundreds to thousands), so the
     0.001 weight was presumably chosen to keep it from swamping the other
     two heads' combined loss -- but it also means the completion
     pathway's gradient signal into the SHARED backbone is roughly 1000x
     smaller than delay/priority's, every epoch. The completion head's own
     final layers still get a real (if small) gradient, but the shared
     3-layer encoder is barely shaped by this objective at all.
  2. Duration may simply be a per-node property this graph's relational
     structure has little to add to -- SAM x quantity / machine-count sets
     an operation's planned span directly; which specific machines/workers
     end up connected to it via edges may carry little further information
     about how LONG that span is, unlike delay risk (queue congestion,
     breakdown history) or urgency (deadline proximity), which more
     plausibly do depend on relational/temporal context beyond the node's
     own attributes.

VERDICT: NOT USEFUL AS CURRENTLY TRAINED. Same practical conclusion the
instruction was watching for -- a head that doesn't demonstrate genuine
value beyond visible inputs -- reached by ablation rather than by an
obviously-degenerate accuracy number, exactly the failure mode raw
accuracy alone would have hidden (Arm A's R2=0.29 looks like a reasonably
working regression in isolation). Consistent with Head 2 already having
zero downstream consumers in ga/ or agent/ (confirmed by repo-wide search
before this section was written) -- nothing in the scheduling pipeline
currently depends on this head's output, so this finding changes no
runtime behaviour. No architecture or loss-weighting change was made
without discussing which fix (if any) is worth pursuing: reweighting the
completion loss and re-measuring, or accepting that this target may not
belong on a message-passing model at all, are both legitimate next steps
but neither is this section's call to make unilaterally.

0H.15 -- DISJUNCTIVE (CONTENTION) EDGES: THE FIRST STRUCTURAL FIX TRIED,
        STILL NO BETTER THAN RANDOM -- CLOSES THE FAIR-FIGHT QUESTION

0H.14 closed the fair-fight investigation on the graph THIS PROJECT HAD --
but the literature on GNNs for job-shop scheduling is consistent about
using a disjunctive graph: conjunctive edges (precedence within a job,
which this project already had) PLUS disjunctive edges (direct
operation<->operation edges between operations competing for the same
resource). This project's graph only had the former. Contention reached
an operation two hops away (operation -> machine -> operation), where
standard message passing dilutes it heavily. That leaves a real
alternative explanation for 0H.14's result open: not "graph structure
can't help here" but "this particular graph construction doesn't expose
the relationship that predicts delay." Only one of those is supported by
evidence up to 0H.14. This section tests the other one, changing exactly
one variable.

SCOPING, MEASURED BEFORE WRITING ANY EDGE-BUILDING CODE (per instruction --
report the count, don't silently pick a restriction): two candidate
definitions of "compete for the same resource," both checked against the
real database first.

  A. (operation's MAJORITY historical line, canonical operation_type)
     pool, from real per-lot leak-free assignments -- the same (line,
     type) granularity Section 1's own load tracking already uses.
     426 pools, size min=1 max=339 median=9.5 (mean pulled up by a few

0H.16 -- PERMUTATION-FLOWSHOP CHECK: THE GA ALREADY SETTLES ON A
        (NEAR-)PERMUTATION SCHEDULE WITHOUT BEING FORCED TO

[REQUALIFIED by Section 1.2.1, the largest correction of the five: "this
factory IS structurally a permutation flow shop" is UNCONFIRMED, resting on
0H.6 which is now known to be synthetic-model-only. Real data found since
(GarmentSmv/LayoutType varying by garment type) suggests the real factory
may not fit this problem class at all. The empirical GA measurement below
still holds as true of this synthetic model; the literature-problem-class
framing does not.

UPDATE, Section 1.3, FURTHER CONTRADICTED: not just unconfirmed for the
real factory anymore -- false of THIS codebase's own synthetic model too.
Routing length (6-10 steps) and structure now vary by garment-type group;
this dataset is a general job shop with type-dependent routing, not a
permutation flow shop, even as a modelling idealisation. The GA-behavior
measurement below has not been re-run on a structure that no longer has
the property the whole experiment was testing for.]

This factory is structurally a permutation flow shop (F_m|prmu|C_max):
every order passes through the same 5 stages in the same order (0H.6).
The textbook representation for this problem class is a PERMUTATION
SCHEDULE -- one global job order applied consistently at every stage --
and NEH/Iterated Greedy, the established heuristics for it, both search
directly over that representation. This project's chromosome does not:
the OS gene is a flat permutation over every (order, stage) pair, and
`order_crossover` + `repair_precedence` can structurally produce a child
where order A leads order B at stage 1 but trails it at stage 2 --
`repair_precedence` only restores each order's OWN routing order (step
i before step i+1), never cross-order consistency at a shared stage. So
the question was live: is the GA's own evolved output actually drifting
away from permutation-schedule structure, and would forcing it to stay
on that manifold (an order-level permutation representation, with its
own crossover/mutation, replacing the current operation-level one)
recover anything?

METHOD (cheap check first, matching the 0H.9/0H.11 pattern -- confirm
there's something to gain before building a new representation):
measured a STAGE-CONSISTENCY metric on real chromosomes -- for every
pair of orders sharing 2+ stages, do they appear in the same relative
order at EVERY shared stage ("consistent") or does the relative order
flip between stages ("inconsistent", i.e. one order overtakes the other
partway through)? Sanity-checked against synthetic cases first: a
hand-built order-major sequence scored 1.0, a deliberately reversed pair
scored 0.0, and a fully random shuffle of 50 orders x 5 stages scored
0.044 (close to the ~1/16 chance rate 5 independent random stage-orders
predicts) -- the metric measures the real thing.

Two real windows, since window 1 alone would repeat 0H.11's own
ceiling-effect mistake (the least-congested window can't show a
difference regardless of mechanism): an uncongested 60-order window
(on-time already 100% for the raw heuristic -- no room to move) and a
genuinely congested 800-order window (CriticalRatio-raw on-time 72.5-
74.2% across runs -- real headroom). CriticalRatio's own raw
construction (order-major emission -- see ga/heuristics.py's
_emit_by_order_priority) is ALREADY a valid, textbook permutation
schedule by construction, so it serves as the natural "always
consistent" reference point; the question was whether the GA's evolved
output stays that way.

RESULT -- exploratory pass (pop=30/gen=15, one seed, 800-order window):
GA-evolved best measured EXACTLY 1.000000 stage-consistency (0 of
319,600 order-pairs inconsistent) while improving on-time rate from
74.2% to 99.2% and fitness by 18% over CriticalRatio-raw, entirely via
line/machine-count (LA/MC) tuning -- striking enough, given this
project's own prior mistake with a comparison that structurally
couldn't show a difference (0H.11's zero-jitter tie-break error), to
demand a robustness pass before treating one run as decisive.

ROBUSTNESS PASS (production scale, per run_final_pipeline.py's own
POP, GENS = 50, 50 -- three seeds, same 800-order window):

  run                              stage-consistency   fitness   on-time   mean tardiness
  CriticalRatio (raw)                    1.000000       3680.4    72.5%       215.4h
  GA seed=7                              0.987475       3036.9    92.8%       118.5h
  GA seed=123                            1.000000       3037.3    93.4%       124.8h
  GA seed=2026                           1.000000       3037.4    93.4%       124.9h

The refined finding: NOT an absolute law. One of three production-scale
seeds (seed=7) measured genuine, if tiny, drift -- 4,003 of 319,600
order-pairs (1.25%) inconsistent -- confirming the structural concern is
real and does occasionally manifest. But the other two seeds landed at
exactly 1.000000, and critically, the seed WITH drift did not score
worse than the two without it: seed=7's fitness (3036.9) and mean
tardiness (118.5h) are the BEST of the three, not the worst, and its
on-time rate (92.8%) is within 0.6 points of the other two. Across all
three seeds, fitness and on-time rate are effectively indistinguishable
regardless of how consistent the winning individual happened to be. All
three comfortably beat CriticalRatio-raw by ~18% fitness and ~20 points
of on-time rate, and in every seed that margin traces to LA/MC (line
and machine-count) tuning, not resequencing -- the OS array stayed
(near-)unchanged from an already-consistent, order-major-derived
starting point throughout.

VERDICT: the structural concern that motivated this check is real (drift
can happen -- confirmed directly, not merely theoretical) but its
practical magnitude is negligible (1.25% of pairs, one seed of three,
zero measurable cost or benefit in the outcome metrics) and selection
pressure alone -- with no explicit constraint anywhere in the code --
keeps the GA within a fraction of a percent of the permutation-schedule
manifold on its own. Building the order-level-permutation representation
NEH/Iterated Greedy use (a real undertaking: new OS gene, new crossover/
mutation, a rolling-horizon comparison) would very likely be a no-op
against current performance, since the GA already sits almost exactly
where that constraint would force it, while strictly narrowing the
search space the LA/MC tuning above actually uses to produce its gains.
Not built. Two findings worth keeping on the record precisely because
they are independent of each other: (1) this GA converges to a
near-permutation-consistent schedule under ordinary selection pressure,
without ever being told to -- the literature-standard structure emerges
here rather than needing to be imposed; (2) on the congested window, the
GA's entire ~20-point on-time-rate gain and ~18% fitness gain over the
best classical heuristic came from resource allocation (which line, how
many machines) rather than from resequencing -- this system's GA
earns its keep on WHERE work runs, not WHEN work is ordered, which is
a genuinely different conclusion from what motivates NEH/Iterated
Greedy's whole approach (both are pure resequencing methods).

Consistent with 0H.9's MC-ceiling result and 0H.11's urgency-tiered
result -- a third independent line of evidence that resequencing
interventions do not move outcomes much in this system, this time from
the literature-standard direction rather than a heuristic one, and this
time with a positive mechanism identified (LA/MC tuning) rather than
only a negative one ruled out.

1.2  MODELING ASSUMPTIONS VS REAL-WORLD DATA
-------------------------------------------------------------------------------

The company's real data files (WorkStation.xlsx, grid.xls, and real order/
PPC records) surfaced five places where data_generation/seed_database_fixed.py
generates something materially unlike the real factory, rather than deriving
it from the real files it already partially reads. Each is reported here
whether or not it was adopted -- the point is documenting the gap honestly,
not selecting the findings that flatter the numbers.

1.2.1  ROUTING IS A SINGLE HARDCODED 5-STEP TEMPLATE FOR EVERY PRODUCT --
       HIGHEST-RISK FINDING, NOT YET RESOLVED

seed_database_fixed.py: `for step in range(1, 6): m_type = machine_types[step-1]`
-- every product, regardless of its randomly-assigned category label, gets
the identical 5-step routing (Body Assembly -> Seam Edge Overlock ->
Flatlock Hemming -> Bar-Tack Pocketing -> Tubular Sleeve Join, always in
that order, always ending in Tubular Sleeve Join). The real product grid's
`Layout` column -- never read by the seeder -- is a plausible real routing/
line-configuration identifier for the 15 real garment types.

WHY THIS IS THE HIGHEST-RISK ITEM OF THE FIVE, MATERIALLY DIFFERENT FROM
THE OTHERS: it is not just a metric-accuracy question, it is the causal
premise several already-published findings are built on. Sections 0H.3,
0H.6, 0H.9, 0H.11, and 0H.16 all trace their result back to "Tubular Sleeve
Join is a fixed, mandatory LAST step for every order" -- true in this
dataset only because the seeder hardcodes it uniformly across every product.
If real routings vary by garment type, the structural-bottleneck narrative
several rounds of GA/heuristic experiments were interpreted through may be
an artifact of one template rather than a real factory property.

STATUS: CHECKED against all four real data files (grid.xls, WorkStation.xlsx,
Plan.xlsx, PPC-1.xlsx). Verdict: the specific 5-step template (these five
machine types, this operation-name sequence, Tubular Sleeve Join always
last) has NO grounding in the real data at all -- it was not simplified
from a real routing, it was invented. None of the four files contain an
operation/process-step table for any product -- no column anywhere lists
"step 1: X, step 2: Y" for a garment type. seed_database_fixed.py's
`machine_types = ["Single-Needle Lockstitch", ...]` list is introduced with
no comment, no citation, no derivation from any loaded file.

What the real files DO contain, and what it implies:
  - grid.xls's `Layout` column (never read by the seeder): NOT a per-
    garment-type routing template. It is far too granular -- a single
    GarmentType ("Pant") spans 138 distinct Layout values, while each
    Layout value maps to exactly one GarmentType. This is a per-style/
    per-production-run identifier (plausibly a cutting-marker or line-
    balance document number), not a reusable "recipe" per garment category.
  - Plan.xlsx's `LayoutDocNo` (also never read): same pattern -- 225
    distinct values, with dozens of distinct LayoutDocNo values WITHIN a
    single GarmentType (e.g. "Short" alone spans 45). The actual CONTENTS
    of these layout documents -- which operations, in what order -- are
    not present in any of the four files; only reference numbers are.
  - Plan.xlsx's `GarmentSmv` (Standard Minute Value, i.e. total real labour-
    minutes per unit) varies close to 5x by real garment type: Shirt
    averages 43.8 min, U Neck averages 9.5 min, with Pant/Full Zip Mock
    Neck/Hoodie spread across the range between. Our model assigns every
    product the SAME 5 steps at sam 1.2-3.8 min each regardless of which of
    the 15 GarmentType labels it randomly draws -- that label is currently
    decorative, not a driver of anything downstream.
  - Plan.xlsx's `LayoutType` (P/H/W) correlates strongly with GarmentType
    (Polo: 98 H vs 1 P; Tank Top: 81 H vs 1 P; Short: 162 P vs 15 H vs 7 W)
    -- a real, garment-type-linked process/configuration distinction our
    model has no equivalent of.

CONCLUSION, STATED PLAINLY: there is no real operation-sequence data
available to this project to confirm OR refute whether a fixed final-stage
funnel exists in the real factory, because that data (the contents of the
real layout documents) was never part of the four files provided. What real
data IS available -- large, garment-type-correlated variance in total work
content and process configuration -- points AWAY from "every product follows
one identical routing," not toward it. The synthetic model's uniform
5-step, TSJ-always-last routing is confirmed to be a property of the seeder
only, with no real-data support for treating it as a discovered fact about
this factory.

findings were, because a correction this size deserves the same clarity:

  0H.3 (window-collapse: resource-type contention compounds) -- its own

  0H.6 (Tubular Sleeve Join: root cause, not a capacity shortage) -- THE

  0H.8 (bottleneck-aware machine selection, measured no-op) and 0H.9

1.2.2  RELEASE-DATE DISTRIBUTION -- TRACK 1 EXECUTED: RELEASE-DATE-AWARE
       FLOOR ADOPTED AS METHOD; CONFIRMS THE 3x/37% FINDINGS ARE REAL, NOT
       MEASUREMENT ARTIFACTS, ON THE CURRENT DATASET

Real order StartDate data: 399-day span, steeply front-loaded (1,765 rows
in the first month, tapering to 43 by the last), ~56 concurrent order-rows
on average (max 324). seed_database_fixed.py's actual generator (lines
~611-624): `scheduled_start_date` for every order is `base_date +/-
random.randint(...)`, a roughly UNIFORM 25-30 day scatter centred on "now" --
nothing like the real shape or span.

Section 2.1's original capacity floor (23.1 days, "the exact dataset in
Section 0") assumed all work is available on day one -- exactly the wrong
comparison if release dates are real and spread out, which is the concern
that motivated Track 1.

TRACK 1, EXECUTED AS A PURE RE-MEASUREMENT (no reseed, no model change --
recomputed against the SAME dataset Section 1.1 already measured):

  Floor A (naive, same-day-availability):    30.1 days
    (83,952 machine-days of remaining work / 2,790 usable machines)
  Floor B (release-date-aware): max(Floor A, the latest-released order's
    own release-offset + its own minimum completion time at its own
    tightest machine-type bottleneck):    30.1 days -- IDENTICAL to Floor A

  Release-date spread in the CURRENT dataset: 0.0 to 25.0 days (a 25-day
  span, ~60 orders released per day on average). The last order's own
  release+completion bound (25.2 days) does not exceed Floor A, so
  Floor B collapses to Floor A exactly.

  Achieved makespan: 91.5 days.  Ratio to Floor A: 3.04x.  Ratio to
  Floor B: 3.04x -- UNCHANGED.

RESULT, reported plainly because it does not favour the hoped-for
reframing: on THIS dataset, release-date awareness changes NOTHING, because
the synthetic release-date spread (25 days) is already far narrower than
what the naive same-day floor implies is achievable (30 days) -- there is no
room for release-date timing to be the explanation. The 3.04x makespan gap
and the 37.2% labour utilisation figure (Section 1.1) are CONFIRMED as
genuine scheduling-quality findings on the dataset actually used, not
measurement artifacts of an unfair same-day-availability comparison. The
open question in Section 2.1 (precedence idle time / list-scheduling gaps /
rolling-horizon window fragmentation) stands, unweakened.

WHAT TRACK 1 DID NOT DO: this is a methodology fix (the release-date-aware
floor is now the correct way to compute this comparison, and is adopted as
such going forward), not a data fix. The underlying release-date GENERATOR
is still nothing like the real 399-day, front-loaded distribution -- that
remains open, and fixing it would itself be a reseed-plus-re-validate change
(Track 2 territory: it would very likely also address 1.2.5's concurrency
gap as a side effect, and would let a genuinely tighter, more realistic
floor be computed than either Floor A or B above).

1.2.3  SHIFT STRUCTURE -- TRACK 2 ASSESSED: NOT CONFIG-LEVEL, DOCUMENTED
       AS A MODELING LIMITATION RATHER THAN IMPLEMENTED

Real: WorkStation.xlsx's WorkHour column shows 118 of 141 lines run a
12-hour shift pattern (2 shifts/day), 23 run 8-hour (3 shifts/day). Model:
utils/shift_rotation.py's SHIFT_BANDS is a single hardcoded 3x8h tuple
(Morning 06-14, Evening 14-22, Night 22-06), applied company-wide with no
per-line variation, and seed_database_fixed.py's CREWS_PER_LINE = 3
hardcodes the same 3-shift assumption into crew formation.

COST ASSESSMENT: NOT a config-level change. SHIFT_BANDS/NUM_SHIFTS is a
global constant threaded through the rotation-arithmetic module itself
(shift_index_for_batch, batch_available_at -- the formulas every crew's
whole calendar is derived from), the seeder's batch/crew formation
(CREWS_PER_LINE), and decision_engine's operator-assignment/shift-lookup
code. Supporting two real shift regimes (2x12h on most lines, 3x8h on the
rest) means the rotation math itself must support a variable shift-count
per line, not a different constant -- a genuine, multi-file refactor, not a
value swap. It would also require a reseed and would invalidate every
labour-utilisation-dependent number already measured (Section 1.1's 37.2%,
the SERVICE_LEVEL_WEIGHT/IDLE_LABOR_WEIGHT notes in 2.5, the shift/sourcing
breakdowns) pending re-validation.

DECISION: per the stated rule (config-level -> do it; reseed-plus-
revalidate -> document instead), this is documented as a modeling
limitation, NOT implemented. present_operator_count and every shift-based
labour figure in this document should be read with "assumes a uniform
3x8h company-wide shift pattern; 84% of real lines actually run 2x12h" as
an attached caveat.

1.2.4  PER-LINE WORKER/MACHINE CAPACITY -- TRACK 2 ASSESSED: CHEAPER AND
       LOWER-RISK THAN SHIFTS, RECOMMENDED IF ADOPTED, NOT YET IMPLEMENTED

Real: WorkStation.xlsx's Worker Capacity column varies materially by line
(68 / 34 / 58 in the sampled rows -- roughly 2x spread), plus LayoutType
(P/H/W) and LineType (E/L) categorical distinctions. Model: machines are
assigned `random.choice(line_ids)` (uniform, no capacity weighting) and
each line's crew size is `random.choice([32, 48, 64])` (uniform, unrelated
to that specific line's real capacity) -- WorkHour, Worker Capacity,
LayoutType, and LineType are all present in WorkStation.xlsx and all
currently unread.

COST ASSESSMENT: cheaper and lower-risk than 1.2.3. Reading the real Worker
Capacity value per line and using it to size that line's crew (replacing
the random draw) or to weight machine assignment is a LOCALIZED change to
the seeder's existing per-line loop -- it does not touch the rotation
formulas' structure (CREWS_PER_LINE's shape is unaffected) and plugs
directly into the per-(line, type) load tracking Section 1(f) already
established as the project's single largest lever, rather than fighting
it. It still requires a reseed (this is baked into synthetic generation,
not a runtime flag) and a pipeline rerun to take effect, so it is not
literally free, but it does not require re-validating the scheduling/GNN
findings the way 1.2.3 or 1.2.1 would -- only the labour-side numbers move.
CAVEAT: its full realism benefit is coupled to 1.2.3 -- plugging a real
68-person capacity into a rotation structure still hardcoded to 3 shifts
per line only partially reflects reality until shift count is also fixed.

DECISION: assessed and recommended if the company wants a labour-utilisation
number that reflects real per-line capacity variation; NOT implemented
this session, pending a decision on whether to schedule the reseed.

2.1  THE MAKESPAN IS STILL 3.1x THE CAPACITY FLOOR
-------------------------------------------------------------------------------
  Capacity floor for the exact dataset in Section 0: 23.1 days
    (64,395 machine-days of remaining work / 2,790 usable machines)
  Achieved: 70.9 days

Section 1(f)'s bound analysis predicted the load-tracking fix would take the
floor to ~27.5 days; the achieved result is 70.9. The bound is a lower bound
that ignores precedence chains and list-scheduling gaps, so it was never
meant to be reached exactly -- but the gap between 27.5 (predicted) and 70.9
(achieved) is real and not yet explained. Candidates, not yet measured:
  - precedence forces idle time even on an otherwise free pool (an order's
    next operation cannot start until its predecessor finishes, wherever
    that predecessor sits)
  - list scheduling (first-come-first-served within a pool) leaves gaps a
    smarter insertion could fill
  - the rolling horizon's window-to-window handoff: each window after the
    first inherits an already-fragmented floor (see 2.2)

2.2  ON-TIME COLLAPSES ACROSS LATER WINDOWS -- STILL OPEN, TWO FIXES RULED OUT
-------------------------------------------------------------------------------
  Current authoritative run (Section 1.1), 5 windows, 300 orders/window:
  win 1: 100.0%   win 2:  98.0%   win 3: 77.0%   win 4:  7.3%   win 5:  0.3%

  Earlier full-book run (Section 1(j), different reseed):
  win 1: 100.0%   win 2:  99.3%   win 3: 80.7%   win 4: 25.3%   win 5:  6.3%

Same collapse pattern in both runs, sharper in the current one -- this run's
fresh reseed happened to produce a more front-loaded order book (see Section
1.1). Consistent shape either way: an unremarkable window 1, then a steep
fall from window 3 onward as later windows inherit an increasingly committed
floor. Nothing below this point in 2.2 depended on the exact percentages, so
the diagnosis and the ruled-out fixes stand unchanged.

Not a capacity wall -- the achievable ceiling for this factory was separately
computed (both a capacity relaxation and a tighter critical-path bound) at
100%; 0 of the orders checked were structurally infeasible even running
completely alone. The later windows are late because they inherit a floor
already committed by everything scheduled before them.

TRIED, BOTH RULED OUT -- see Section 0B for the full measurements:
  - Widening the lookahead beyond the commit size (textbook receding-horizon
    control): on-time 71.3% -> 65.9% -> 63.1% as lookahead widened from 300
    to 600 to 900 orders, at ~2.8x the runtime. Worse, monotonically.
  - Shrinking the commit chunk instead (the more literature-standard
    frequent-rescheduling pattern): on-time 66.0% -> 57.7% (commit 100) /
    62.9% (commit 150) against a same-run baseline, at ~1.6x the runtime.
    Also worse.

Both point at the same diagnosed cause rather than two different problems:
the fitness function optimised over whatever is currently visible has no
notion of "committed vs provisional" -- it can sacrifice near-term
punctuality to improve the schedule's average over orders that get discarded
and re-optimised next round regardless. Widening lookahead gives it more such
orders to trade against; shrinking the commit size makes that trade happen
more often. Neither changes the underlying symmetry.

STILL OPEN. The direct next step, not yet built: differentiate the objective
so it weights (or exclusively scores) the commit-window orders rather than
treating the whole lookahead symmetrically -- either restrict the fitness
function's lateness/tardiness terms to committed orders only, or apply a
discount factor that fades in the tail. That is a different, more surgical
change than tuning window geometry, and it is what standard receding-horizon
control actually does when it works.

TWO RELATED PROPERTIES, CONFIRMED (not just assumed) DURING THIS
INVESTIGATION, both against real exported data spanning the full run:
  - An order's operations never split across two committed windows: 1,263
    orders partition exactly across 5 exported files, zero overlaps, zero
    splits (tests/test_rolling_horizon_integration.py).
  - Batch shift-rotation/rest-day availability is evaluated fresh per
    operation, not cached across a window: 39,894 crew-member assignments
    spanning 7 distinct real weeks, each independently recomputed for its
    own date, zero mismatches (same test file).

2.3  THE DELAY LABEL IS STILL NOT A PREDICTION TASK
-------------------------------------------------------------------------------
Re-confirmed in the current authoritative run (Section 1.1): delay_accuracy
0.9293, precision/recall/F1 all 0.0000, AP 0.071 -- EXACTLY the no-skill
baseline (this run's positive rate is also 0.071) -- and ROC AUC 0.513, barely
above the 0.500 coin-flip line. Delay probability range 0.0856-0.0973 across
every operation in the graph: the model predicts a near-constant value for
everything, just as in every earlier run, though the exact base rate a fresh
reseed produces varies (0.32-0.39 in the run this section originally
described, 0.071 here) -- see Section 1.1's note on why. This is now measured
via AP/ROC AUC (this project's lead metric for delay, see models/evaluate.py)
rather than accuracy alone, per the deeper investigation in Section 0H.12-
0H.15, which reached the same conclusion from multiple independent angles
(fair-fight ablation against LinearRegression/RandomForest, and a literature-
standard disjunctive graph retest) and closed the question.

Root cause (established earlier, unchanged): the label MAX-aggregates a
per-lot delay flag over 60 lots, so it is 99.88% identical to "has this
operation been touched at all" rather than a risk signal. Ruled out as fixes:
machine current_status (no correlation, assigned before scheduling),
breakdown history (r=0.021), actual start/end times (do not exist in the
schema). This needs the LABEL redefined at the seeder -- a fraction-of-lots
threshold instead of MAX, and delays driven by persistent causes instead of a
memoryless coin flip. Deliberately NOT done this project, per standing
instruction: report honestly as a limitation, revisit only if genuine spare
time remains.

Consequence acted on: the duration-inflation buffer this near-constant
prediction was driving (RISK_BUFFER_AT_CERTAINTY) is disabled at 0.0 until
the label predicts something real. Restoring it is correct the moment it does.

===============================================================================
SECTION 3 -- THE GNN, HONESTLY
===============================================================================

A three-arm controlled ablation (identical GA seed, one graph build) tested
whether the GNN's predictions do anything to the schedule:
  Arm A: real model inference
  Arm B: flat constants (delay=0.0, priority=0.5)
  Arm C: constants set to the model's OWN mean output

Arm A and Arm C agreed within 0.35% on every metric. Arm B -- with the risk
buffer removed entirely -- beat both on every metric, by almost exactly the
size of the buffer's own padding factor. Conclusion: the delay head carries
no per-operation information; its only effect on the schedule was a uniform
tax proportional to its base rate. This project's response, given the
constraint against redefining the label: disable the buffer (Section 2.3),
keep the GNN wired into the pipeline (the plumbing is correct and becomes
valuable the moment the label is fixed), and report the finding rather than
hide it.

A brief literature check confirmed the general GNN+scheduling approach is
reasonable but not the field's dominant one: most recent work pairs a GNN
state ENCODER with a trained RL policy (typically PPO), not a GA optimiser --
a different architecture, not an upgrade path from what is built here, and
not pursued given the risk of discarding validated infrastructure this late.
What IS directly relevant is Kurdi et al.'s island-model GA for job-shop
scheduling, built explicitly against premature convergence -- the exact
technique tried in Section 1(h), and the exact reason it was tried. RL is
recorded here as acknowledged future work, not attempted this project.

SECTION 4 -- ON METHODOLOGY: EIGHT REVERSALS
===============================================================================

This project's discipline was measure before declaring victory, every time,
including when a prior claim (the assistant's or the supervisor's) turned out
wrong. Eight cases where a plausible-sounding narrative was built from a
result's shape and then reversed once actually checked:

  1. "The order book is over-committed against capacity" -- inferred from a
     sharply degrading rolling-window on-time curve. Checked with two
     independent bounds (a capacity relaxation and a tighter critical-path
     bound): the ceiling is 100%, not something less. 0 orders were
     structurally infeasible. The degradation is a scheduling artefact
     (Section 2.2), not a sales-vs-capacity wall.

  2. "A 300-order rolling window gives ~3.5x the full-book throughput" --
     extrapolated from window 1 of an isolated single-window sweep, which is
     the only window that starts on an idle floor. A genuine multi-window
     validation with machine state carried forward measured no real
     throughput difference (12.4 vs 12.0 orders/day); the real benefit is
     on-time rate (52.6% vs 26.7% at the time), from sequencing discipline,
     not speed.

  3. "The GA is losing to dispatching baselines by up to 115%" -- measured
     immediately after the load-tracking fix, in a rolling multi-window run.
     Impossible on its face, since the best baseline is seeded into the
     population and protected by elitism. Cause: run_baselines() was not
     inheriting the carried-forward machine state, so baselines were scored
     against an idle factory while the GA faced the real inherited floor --
     the metric was measuring a head start, not the algorithms. Fixed.

  4. "Local search does not help" -- the first implementation used 4 of a
     400-evaluation budget and finished in under a second, because it gave
     up after one failed pass across three move types. Looked like a clean
     negative result. It was a climber that barely ran; fixed to draw until
     budget or a patience threshold, after which it did move 2 of the 3
     windows the GA's own operators left completely untouched.

  5. "Overlapping lookahead will fix the window-collapse problem" -- the
     textbook diagnosis (Section 2.2's original wording) said a wider
     lookahead was "the direct way to attack this." Implemented and measured
     at L=300/600/900 (Section 0B): it made on-time rate, makespan,
     throughput and labour utilisation all monotonically WORSE, at ~2.8x the
     runtime. Tried the more literature-standard variant next -- shrink the
     commit chunk instead (commit=100/150 against a moderate lookahead) --
     on the theory that frequent, small commitments might sidestep the same
     failure mode differently. Also worse, at ~1.6x the runtime. Neither
     textbook window-geometry technique helps this system -- the fitness
     function needs to be told which orders are actually being committed
     before either variant can pay off.

  6. "Scoring only the committed orders will fix the window-collapse
     problem" -- the natural next step after reversal 5, and the direct
     implication of its own diagnosis. Implemented (Section 0C) and measured
     across the same five arms, same-process, fix active throughout. Only
     partly true: it substantially shrank the harm of a 2x lookahead/commit
     ratio (-5.5pp degradation before, -0.5pp after) but left a 3x ratio
     roughly as bad via lookahead widening (-7.7pp vs -8.2pp) and made a 3x
     ratio WORSE via commit-shrinking (-10.6pp vs -3.0pp before the fix, on
     the C=150/L=450 arm) -- the opposite of what fixing the objective was
     supposed to do to that arm. No tested geometry, fixed or not, beats the
     plain non-overlapping baseline. Diagnosed why (Section 0C): the fix
     removes provisional orders' only reason to be scheduled sensibly, and
     that cost grows with the uncommitted fraction. NOT adopted; the
     production default (no lookahead, no commit-shrinking) is unchanged.

  7. "Averaging each operation's ~60 lots' individual lateness will give the
     GNN a genuine plan-vs-actual delay signal" -- the first implementation
     of the Section 0D fix. Retrained and measured: positive_rate=0.0000,
     a SECOND degenerate label, different from the execution_status one it
     replaced but equally useless. Diagnosed and confirmed against the live
     database: averaging ~60 independent per-lot variance draws crushes the
     spread by the Central Limit Theorem to well under the 20% threshold --
     arithmetic, not a modelling problem. Fixed by matching how an
     operation's completion actually works (gated by its LAST lot to
     finish, not an average across all of them) and by comparing against
     the right scale (a single lot's duration, not the whole multi-lot
     span) -- confirmed at a real 7.7% positive rate before retraining
     again. Caught by the same discipline as everything else here: retrain,
     then measure, before calling it done.

  8. "Exposing machine breakdown status and queue congestion at dispatch
     time will give the delay classifier real, fairly-tested causal
     features" -- the Section 0E feature-engineering follow-up's own
     assumption. Retrained and measured (AP/ROC-AUC no better than Section
     0D, arguably worse), which on its face looked like confirmation that
     delay is memoryless noise. Checked with a raw correlation pass against
     the four new features directly (bypassing the GNN) before accepting
     that: two of the four -- machine_status_at_dispatch and
     queue_delay_mins_at_dispatch -- were IDENTICALLY CONSTANT across all
     7,500 operations, for two distinct, root-caused reasons (queue delay
     measured against a shift-snap function that has been a silent no-op
     since the 3-shift model was built; machine breakdown status checked at
     a point in the simulation that can structurally never read
     'Breakdown' for an assigned machine, given how free-time bookkeeping
     works). Only the other two features -- deadline budget and
     employee-leave fraction -- were genuinely tested, and only for those
     two does "no correlation" actually hold. The clean "memoryless noise"
     narrative would have been accepted from the retrained metrics alone;
     verifying the inputs first turned it into a narrower, more accurate
     finding plus a concrete, not-yet-built fix for the two dead features.
     RETESTED after fixing both (queue delay against prev_end; machine
     health as persistent breakdown-count history, re-checking the old
     "breakdown history r=0.021" finding fresh first rather than assuming it
     still held): AP 0.101 and ROC AUC 0.543, both real, both the best this
     project has measured for this classifier since the original label was
     retired. Confirmed both features now genuinely vary before trusting
     that number. Their INDIVIDUAL raw correlations with the label are still
     small (|r| < 0.05, same band as everything else measured this
     session) -- the improvement is real but not fully explained by any
     single pairwise check, and should be read alongside Section 0F's
     independently-discovered train/val leakage finding (72.8% of
     validation nodes have message-passing exposure to a same-order training
     sibling), not in isolation. See Section 0E.

Each of these is reported here not as an embarrassment to smooth over but as
the methodology working as intended: a plausible story got proposed, and got
checked before being written down as a finding.

5.2 -- DELAY CLASSIFIER AP VS. ITS OWN THEORETICAL CEILING: NOISE, NOT
       LEAKAGE, NOT ABOVE THE CEILING EITHER

DELAY_LABEL_FIX_PROPOSAL.md's DGP ceiling section (AP=0.1574) previously
read the GNN's measured AP (0.159-0.172) as "already AT OR ABOVE this
ceiling" -- an on-its-face implausible result for a synthetic, mechanically
computed oracle bound. Live re-measurement of the current production
checkpoint reproduced the cited range almost exactly: AP 0.1723, ROC-AUC
0.5579, positive rate 0.1118.

Two hypotheses tested directly, not just proposed:
  - LEAKAGE VIA CONTENTION EDGES. Found a real, previously unaudited
    exposure -- see 5.3 below -- but a direct inference-time ablation
    (removing val<-train contends_with edges, same trained weights) barely
    moved the number: 0.1723 -> 0.1715. Ruled out as the cause of the
    ceiling result specifically.
  - SAMPLING NOISE. Bootstrapped the model's own AP, 3,000 resamples of the
    1,744-node validation set (195 positives): 90% CI [0.1424, 0.2200]. The
    0.1574 ceiling sits at the 19th percentile of that distribution --
    comfortably inside ordinary estimation noise for a sample this size.

VERDICT: the classifier's AP is statistically indistinguishable from its
theoretical ceiling, not clearly above it. DELAY_LABEL_FIX_PROPOSAL.md's
"already AT OR ABOVE this ceiling" line has been corrected in place
(2026-09-01) to this framing. Practical conclusion is unchanged either way:
no evidence of exploitable signal being left on the table.

5.3 -- CONTENDS_WITH CONTENTION-EDGE EXPOSURE: FOUND, SCOPED, NOT CLOSED

While investigating 5.2, found that the graph's operation<->operation
contends_with edges (graph/edge_builder.py::build_disjunctive_edges,
Section 0H.15) give 100% of validation nodes direct message-passing access
to a mean of 1,627 training nodes each (max 2,101) -- larger in raw count
than the 72.8% precedence-edge exposure Section 0F/0G already found and
fixed by switching to an order-level train/val split.

SCOPING DECISION: NOT the same class of gap, and NOT closed, for a
structural reason rather than a convenience one:

  - Precedence edges connect operations WITHIN one order (~1,497 orders,
    fine-grained), so grouping the split by production_order_id closed
    that channel completely -- an order's operations are never split
    across train/val, so same-order neighbours are never on the other
    side.
  - contends_with pools are operation_type ONLY, company-wide (5 pools
    total, sizes 1,023-2,615, deliberately NOT order-scoped -- that's the
    entire point of modelling a shared machine-type resource pool, see
    Section 0H.15's own reasoning for dropping line-scoping). There is no
    finer grouping unit available to split on: the "groups" for this edge
    type ARE the 5 operation types, and every validation node belongs to
    one of them by definition. A val node's ~1,600 same-type train
    neighbours is not an artefact of an arbitrary split choice the way the
    precedence exposure was -- it is very close to the full pool minus the
    ~20% held out (pool size x ~0.8 matches the measured mean almost
    exactly), unavoidable for ANY split of this graph.
  - Unlike precedence (a genuinely novel future order's own earlier
    operations would never be pre-existing "training" data), a genuinely
    novel order's operations WOULD, in real deployment, contend with the
    full company-wide pool of contemporaneous same-type operations --
    most of which are already-known, not withheld. The val<->train
    exposure here reflects the graph's real production topology, not a
    leak created by evaluation methodology.
  - Empirically ruled out as material to the one metric it was suspected
    of inflating (5.2's AP-ceiling question): 0.1723 -> 0.1715 under
    direct ablation.

Documented here as the record this exposure was missing; not scheduled for
a code fix. If it is ever revisited, the honest framing is "how much does
company-wide contention information help, structurally unavoidable at this
pool granularity" -- not "leakage to be closed."

5.9 -- HUMAN-READABLE RUN REPORT GENERATOR: BUILT AND TESTED

reporting/run_report.py reads outputs/authoritative_comparison_report.json,
outputs/proposed_schedule.json, outputs/order_completions.json and an
optional breakdown log, and writes outputs/run_report.md -- four sections
(executive summary, order highlights, disruption narrative, honest
caveats), every figure sourced from real fields, tier codes translated to
plain sentences. 11 tests in tests/test_run_report.py, all passing,
isolated from the repo's real output directory. Deliberately NOT wired

separate script (run_authoritative_comparison.py) with a different scope
and runtime -- auto-wiring would silently pair a fresh schedule with a
stale comparison report.


===============================================================================
HOW TO REPRODUCE
===============================================================================

Single command, from the project root:

    python run_final_pipeline.py

Reseeds the database (BACK IT UP FIRST -- TRUNCATE auto-commits and cannot be
rolled back), builds the graph, trains the GNN, evaluates it, schedules the
full order book across rolling windows (commit-only by default -- see
Section 0B on why lookahead is not enabled) with local-search polishing,
exports the operational schedule for every committed window, runs a breakdown
simulation, and generates the standing evaluation report. ~35-45 minutes on
this machine (CPU-only torch, 16 GB RAM). Writes:

  outputs/final_run_report.json     every stage's timing and metrics
  outputs/evaluation_report.txt     human-readable standing report
  outputs/evaluation_report.json    the same data, machine-readable
  outputs/plots/*.png               PR/ROC curves, GA convergence,
                                     local-search gain, labour breakdowns

  mysqldump -u root -p --single-transaction --routines --triggers \
      --databases garment_fyp_db > backups/garment_fyp_db_$(date +%F).sql

Individual stages remain runnable separately for development:

  python -m graph.graph_builder     # ~37s
  python -m models.train            # ~14min
  python -m models.evaluate         # ~30s
  python -m models.inference        # ~30s
  python -m ga.scheduler            # ~20s, small smoke test
  python -m agent.fuzzy_logic       # instant, pure python, no DB
  python -m agent.decision_engine   # full single-pass reschedule
  python -m pytest tests/           # 296 tests, ~20-90s
  streamlit run frontend/dashboard.py
